# 07. 通知 / 日付 / タイムゾーン

## 1. 通知の製品仕様

通知は**「猫と今日の習慣を振り返る時間」**として実装する。習慣ごとの督促ではない。

- 最大2枠、各枠に時刻と曜日集合。初期状態はOFF。
- 初回設定では本人が時刻を選ぶ。勝手に就業時間/就寝時間を推測しない。
- 通知タイトルは固定の製品/猫の案内、本文は汎用の短文。習慣名、未達数、健康情報、愛情不足を表示しない。
- 通知tapはHomeへ。ロック画面から完了/取り消し操作は初期版に入れない。
- バッジなし。通知音は初期版なし。端末を振動させるための独自バックグラウンド処理なし。
- 設定曜日・時刻に届くため、既に全件記録済みでも通知されることがある。この挙動を通知設定に記載する。

アプリが動いていなくても、登録済みローカル通知はOSの機能で扱える。ただし通知の実際の表示・時刻は集中モードなどOS側の判断に影響され、到達は保証されない。[S04]

## 2. なぜ習慣別にしないか

ローカル通知を長期間先まで作って「未達の時だけ」「日に応じた会話」にしようとすると、アプリが開かれない時の予定補充や状態反映に制約が生まれる。v1は単純な曜日繰り返しにして、バックグラウンド処理が常時動く前提を除く。

通知文で「まだ終わってないよ」と断定しない。今の達成状態をOSが自動参照して通知を変えるわけではない。

## 3. 実装

各slot × weekdayに`UNCalendarNotificationTrigger`（repeats=true）を1件。最大14件。毎日という特殊ケースに依存せず、曜日7件に統一してテストを容易にする。[S04]

domainはISO weekday（月1〜日7）。Apple Calendarのweekday（日1〜土7）へ`iso % 7 + 1`で変換する。DateComponentsは必要なweekday/hour/minuteだけを指定し、意図しないyear/month/dayを混ぜない。

identifier例: `nikucue.reminder.v1.<slotUUID>.weekday.<isoWeekday>`。
通知を変更/停止するときはこのprefixのpending requestだけを差分更新。起動ごとに別UUIDで重複作成しない。

設定変更、言語変更、全データ削除、復元後、権限変更後のforegroundでreconcile。復元直後はOFF。成功した登録数と設定を整合させ、OS登録エラーをユーザーへ隠さない。

タイムゾーンは通常、端末の現在のローカル時刻に追従する設計。Calendar/DateComponentsへのtimeZone設定を固定UTCとして保存しない。採用OSでの時差移動・夏時間の挙動は実機確認し、実際と違う保証文を入れない。

## 4. 権限

通知機能を選んだ瞬間に説明→OS許諾を要求。拒否しても利用可能。[S05]
過去に拒否済みなら再び同じOSダイアログが出ると仮定せず、設定アプリへの導線を表示する。
foreground表示中は通知bannerを重ねて出さず、現在画面を維持。notificationsのdelegateを早期に接続し、起動途中のtapはDB readyまで保留する。

## 5. 日付キー

保存キーは`YYYY-MM-DD`、Gregorian、ASCII digits。UIがタイ語/仏暦でも保存年を2569に変えない。端末locale任せのDateFormatterをDBキーに使わない。

記録時点の端末ローカル日をdayKeyにする。加えてUTC timestampとtimeZoneIDを保存。既存記録のdayKeyは旅行しても変えない。

日付の差分はCalendarの日単位演算で求める。`seconds / 86400`で何日かを計算しない。夏時間と移動をテストする。

端末の時計を操作した場合も、1habit/同じdayKeyの二重記録はしない。ゲーム内経済はないため、不正対策サーバーを追加しない。ユーザーが戻った地域で同じ日を再び過ごしても同じdayKeyへ統合される。これはv1の意図した制限。

UIの日付はユーザーlocaleで表示してよい（タイ語の仏暦表記も可）が、画面編集をdayKeyへ変換する時は必ず明示的CalendarServiceを介す。タイ語localeは時刻が24時間制だと決めつけず端末設定を尊重する。

## 6. 必須テスト

タイ語+仏暦、バンコク/東京/インド、夏時間の開始終了、23:59から翌日、background中の日跨ぎ、通知拒否→設定で許可、週末だけ、同じ時刻2枠（保存時に重複を禁止）、言語切替、30日アプリ未起動、時差移動、再インストール、復元による通知重複。

「30日未起動でも予定の補充が不要」は繰り返し設定からの設計意図。実際の到達時刻を保証する試験ではない。
